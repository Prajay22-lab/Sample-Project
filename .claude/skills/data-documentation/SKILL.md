# Data Documentation Skill

## Documentation Hierarchy

| Level | What to Document | Where |
|-------|------------------|-------|
| Column | Definition, source, edge cases | schema.yml |
| Model | Purpose, grain, owner, SLA | schema.yml + docs blocks |
| Domain | Business context, relationships | docs/domain.md |
| Project | Architecture, conventions, setup | README.md |

## Column Description Requirements

Every column description MUST include:

1. **What it is** - Business definition in plain language
2. **Where it's from** - Source system or calculation logic
3. **Gotchas** - Nullability, edge cases, known issues

### Column Description Template

```yaml
columns:
  - name: customer_id
    description: >
      Unique identifier for a customer account.
      Source: Stripe customer ID (cus_xxx format).
      Never null. One customer may have multiple subscriptions.
    tests:
      - unique
      - not_null

  - name: customer_lifetime_value
    description: >
      Total revenue from this customer since first order, in USD.
      Calculated as SUM(order_total) from fct_orders where status != 'cancelled'.
      NULL for customers with no completed orders.
      Updated daily; not real-time.
    tests:
      - not_null:
          where: "first_order_date IS NOT NULL"

  - name: churn_risk_score
    description: >
      ML-predicted likelihood (0-100) of churning within 30 days.
      Generated by propensity model v2.3 (see docs/ml-models.md).
      Scores >70 trigger automated retention workflow.
      NULL for customers <90 days old (insufficient data).
      Refreshed weekly on Sundays.
    
  - name: created_at
    description: >
      Timestamp when the record was created in source system.
      Source: Stripe API created field.
      Always UTC. Never null.
    tests:
      - not_null
```

### Description Anti-Patterns

```yaml
# ❌ BAD: States the obvious
- name: customer_id
  description: "The ID of the customer"

# ❌ BAD: Too technical, no business context
- name: mrr
  description: "DECIMAL(10,2) column from monthly_revenue table"

# ❌ BAD: Missing null behavior
- name: last_login_at
  description: "When the user last logged in"

# ✅ GOOD: Business context, source, edge cases
- name: last_login_at
  description: >
    Most recent login timestamp for the user.
    Source: Auth0 login events.
    NULL if user has never logged in after account creation.
    Updated in real-time via event streaming.
```

## Model Documentation Template

```yaml
models:
  - name: fct_orders
    description: >
      **Grain**: One row per order line item.
      
      **Purpose**: Central fact table for all order and revenue analysis.
      Primary source for Finance and Sales dashboards.
      
      **Key relationships**:
      - Joins to dim_customers on customer_sk
      - Joins to dim_products on product_sk  
      - Joins to dim_date on order_date_sk
      
      **Update frequency**: Incremental every hour.
      
      **SLA**: Data available within 2 hours of order placement.
      
      **Owner**: @analytics-team
      
      **Known issues**:
      - Orders from legacy system (pre-2022) missing product_category
      - Refunds appear as negative quantities
    
    meta:
      owner: analytics-team
      tier: gold
      pii: false
      contains_financial_data: true
      
    columns:
      # ... column definitions
```

## Documentation Blocks (dbt)

For longer documentation, use doc blocks:

```markdown
{# docs/models/fct_orders.md #}

{% docs fct_orders %}

## Order Fact Table

This is the primary fact table for order analysis, capturing every line item 
across all sales channels.

### Business Context

Orders flow from three source systems:
1. **Shopify** - E-commerce orders (80% of volume)
2. **Salesforce** - Enterprise deals (15% of volume)
3. **Manual CSV** - Partner orders (5% of volume)

### Key Metrics Derived

| Metric | Calculation |
|--------|-------------|
| Gross Revenue | SUM(quantity * unit_price) |
| Net Revenue | Gross Revenue - SUM(discount_amount) |
| AOV | Net Revenue / COUNT(DISTINCT order_id) |

### Caveats

- **Refunds**: Appear as separate negative line items, not adjustments
- **Bundles**: Exploded into component products; bundle_id links them
- **Currency**: All amounts normalized to USD at time of order

{% enddocs %}
```

Reference in schema.yml:

```yaml
models:
  - name: fct_orders
    description: '{{ doc("fct_orders") }}'
```

## Source Documentation

```yaml
sources:
  - name: stripe
    description: >
      Payment processor data loaded via Fivetran.
      Sync frequency: Every 6 hours.
      Contact: @data-engineering for sync issues.
    
    database: raw
    schema: stripe
    
    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    
    tables:
      - name: payments
        description: >
          All payment transactions including successful, failed, and refunded.
          One row per payment attempt (not per charge).
        
        columns:
          - name: id
            description: Stripe payment ID (pi_xxx format). Primary key.
          - name: status
            description: >
              Payment status: succeeded, failed, pending, refunded.
              Note: 'refunded' only appears after full refund; 
              partial refunds keep 'succeeded' status.
```

## Data Contract Template

For critical interfaces between teams:

```yaml
# contracts/orders_contract.yml
contract:
  name: orders_interface
  version: 2.1.0
  owner: analytics-team
  consumers:
    - finance-team
    - sales-ops
  
  sla:
    freshness: 2 hours
    availability: 99.9%
    
  schema:
    - name: order_id
      type: VARCHAR(50)
      nullable: false
      description: Unique order identifier
      
    - name: order_total
      type: DECIMAL(12,2)
      nullable: false
      description: Total order value in USD
      constraints:
        - type: range
          min: 0
          
    - name: status
      type: VARCHAR(20)
      nullable: false
      description: Order status
      constraints:
        - type: enum
          values: [pending, completed, cancelled, refunded]
          
  breaking_changes:
    - version: 2.0.0
      date: 2024-01-15
      change: Renamed customer_id to customer_sk
      migration: "JOIN on dim_customers to get original customer_id"
```

## Business Glossary Integration

Link technical columns to business terms:

```yaml
columns:
  - name: arr
    description: >
      Annual Recurring Revenue. See glossary: [ARR](/docs/glossary#arr)
      
      Calculated as: MRR * 12 for active subscriptions.
      Excludes one-time charges and usage-based fees.
```

## Freshness Documentation

Always document data freshness:

```yaml
models:
  - name: fct_daily_sales
    description: >
      ...
      
      **Freshness**:
      - Source data: Real-time from Stripe
      - Model refresh: Daily at 6am UTC
      - Dashboard cache: 1 hour
      - Safe to use for: Previous day analysis
      - NOT safe for: Intraday reporting
```

## Documentation Checklist

Before marking a model as production-ready:

- [ ] All columns have descriptions
- [ ] Model has grain clearly stated
- [ ] Owner/team specified
- [ ] Update frequency documented
- [ ] SLA defined (if applicable)
- [ ] Known issues/caveats listed
- [ ] Source-to-target mapping clear
- [ ] Null behavior documented for each column
- [ ] Related models/dashboards linked
- [ ] Breaking changes documented
